# RK3588 双摄 YOLOv8+RTSP 项目 · 验收测试套件

主机（这台电脑）侧测试工具，通过网络对板子（默认 `192.168.1.50`）做验收。
每个脚本解决验收标准里的**一条或一组可测项**，都带「测什么 / 怎么测 / 怎么判」。

## 输出约定（每个脚本都会自己落日志）
所有脚本把**原始测量数据 + 最终 PASS/FAIL 结论**写进 `artifacts/` 下的日志，同时实时显示在终端：

| 脚本 | 数据/结论落盘文件 |
|---|---|
| 01 | `artifacts/01_livestream_<时间戳>.log` |
| 02 | `artifacts/02_fps_<时间戳>.log` |
| 03 | `artifacts/03_probe_<时间戳>.log`（`--csv` 可另加机器可读行） |
| 04 | `artifacts/stability_<时间戳>.csv`（逐样本数据）+ `stability_run_<时间戳>.log`（过程+结论） |
| 05 | `artifacts/memwatch_<时间戳>.csv`（逐样本数据）+ `memwatch_<时间戳>.log`（过程+结论） |
| 06 | `artifacts/06_perf_<时间戳>.log`（逐采样行 + CPU 摘要） |
| 07 | `artifacts/07_concurrent_<时间戳>.log` + `07_ref_<时间戳>.log`（参考客户端明细） |
| 08 | `artifacts/08_reconnect_<时间戳>.log`（每次断连结果 + 收尾结论） |
| 09 | `artifacts/09_tcp_<时间戳>.log`（逐会话明细 + 结论） |

验收完把 `artifacts/` 整个打包，就是一份带原始数据的验收记录。

## 环境要求
- 主机有 `ffmpeg ffplay ffprobe python3 ssh nc`（已确认存在）。
- 板子 ssh 免密（`ssh root@192.168.1.50` 能直接进）。
- 板上服务已在运行（`/opt/rknn_yolov8_dual ...` 之类，进程名见 config.env）。

## 验收对照总表

| 验收组 | 验收项 | 脚本 | 判定口径（脚本内注释有解释） |
|---|---|---|---|
| ① 功能 | 双路可拉流、中途加入可起播 | `01_livestream_check.sh` | 两路都连续拉 10s 不报错；起播延迟 = 到解码出第一帧的毫秒数（≤1 个 GOP 间隔左右算正常） |
| ① 功能 | 一路故障另一路正常 | 手动（见下） | 拔一路 camera/sensor，另一路 ffplay 不掉 |
| ② 性能 | 实际帧率稳定 30fps | `02_fps_check.sh` | ffmpeg 解码 10s 窗口的帧数换算 fps，≥标称×95% |
| ② 性能 | 码率 CBR 4Mbps | `02_fps_check.sh -b`（抓包统计） | 每秒 RTP 字节 ≈ 4Mbps/8 = 500KB/s |
| ② 性能 | CPU / NPU 占用 | `06_perf_sample.sh` | 进程 CPU 求和、`/sys/kernel/debug/rknpu/load`，留采样记录 |
| ③ 稳定性 | 长时间不掉流不丢包 | `04_longrun_stability.sh` | 循环跑 03 探针，RTP 序列号无缺口、每窗口有包 |
| ③ 稳定性 | 崩溃自恢复 | `08_reconnect_stress.sh` + 手动 kill | 压测后服务仍在、重连都能成功；另可手动 `kill -9` 验证自启 |
| ③ 稳定性 | 内存不增长 | `05_mem_watch.py` | VmRSS 时间序列斜率 ≤ 阈值（默认 10MB/h） |
| ④ 并发/韧性 | 多路 + 慢客户端不互拖 | `07_concurrent_clients.sh` | 参考路探针无缺口，正常客户端不掉帧率 |
| ④ 并发/韧性 | 断开重连不崩 | `08_reconnect_stress.sh` | 反复连接/断开后服务存活、连接仍成功 |
| ④ 并发/韧性 | TCP 结果帧格式 + 重连 | `09_tcp_result_reconnect.py` | 每帧头 magic/version/header_len 校验通过 |
| ⑤ 业务 | 漏报/误报、告警时延 | README「业务验收怎么做」 | 人工 + 板上加两行时间戳日志 |

## 一次完整验收的推荐顺序（先手动后自动化，基线先行）

1. **先打基线**：板上服务稳定运行后，跑 01/02/06 一次，把"正常的数字"存档
   （比如 CPU 30%、fps 30、起播 0.5s）。后面所有判断都以这份基线为参照。
2. **功能**：01（双路）。再手动做"一路故障"测试。
3. **性能**：02（fps/码率）、06（CPU/NPU）。
4. **并发**：07（多客户端+慢客户端），确认架构里的"慢客户端不阻塞"设计成立。
5. **韧性**：08（反复断连），确认服务端不崩、不泄漏连接。
6. **长稳 + 内存**：04 和 05 一起挂上跑（比如 04 每 10 分钟一次共 24h，
   05 每 1 分钟采一次 VmRSS）。这是你简历里"7×24 不掉流 / 内存不增长"的证据来源。
7. **收尾**：`cat artifacts/*.log artifacts/*.csv` 汇总，保留日志 = 验收记录。

## 手动项
- **一路故障另一路正常**：拔掉/停掉 camera0 的 sensor（或让 /dev/video62 不可用），
  持续 ffplay camera1，画面应连续不掉；重启 camera0 后应自动恢复挂载 /live0。
- **崩溃自恢复**：`ssh root@192.168.1.50 'kill -9 <app pid>'`，等自启脚本/看门狗拉起，
  再 ffplay 拉流应能重新出图。
- **业务漏报/误报**：录一段真实场景（人进出、水位变化），现场跑，带时间戳记每次
  告警，人工数漏报（该报没报，安全事件，必须压到接近 0）和误报。

## 各脚本测试思路（学习用）

| 脚本 | 关键测试思想 |
|---|---|
| 01 | 用"解码出第一帧"测起播延迟，等价于用户按下播放到看到画面的时间 |
| 02 | 解码层帧数是最可信的 fps；`-progress pipe:1` 是为了程序化解析 ffmpeg 输出 |
| 03 | 自己实现 RTSP 握手（OPTIONS/DESCRIBE/SETUP/PLAY），才能拿到 RTP 层做序列号连续性统计 —— ffplay 做不到这点 |
| 04 | "长时间稳定性"不是跑一次，而是周期性采小样，能定位"什么时候开始变差" |
| 05 | RSS 曲线只涨不回落是泄漏的典型特征；斜率法消除偶发抖动 |
| 06 | 性能数字必须带时间戳采样存档，面试/汇报才有据 |
| 07 | 慢客户端用 `ffplay + SIGSTOP` 模拟"不读数据"的对端，正好打你非阻塞+有界缓冲的设计 |
| 08 | 压力测试要检查的是"结束后服务还活着、还能服务新连接"，不是只看过程中没报错 |
| 09 | 长度前缀协议的正确性 = 每次能按 header_len 精确切帧、magic 不串 |
